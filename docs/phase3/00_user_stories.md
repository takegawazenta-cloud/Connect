# ユーザーストーリー

Phase2のペルソナ・利用シーンを基に作成。Phase0決定2(デスクモード/セルフサービスモード)に沿い、「誰が入力するか」でストーリーを分けている点が本サービスの設計上の特徴。

## ホテル側(コンシェルジュ)

- ジュニアコンシェルジュとして、ゲストの曖昧な要望を入力すると、追加で聞くべき質問を提示してほしい。**なぜなら**経験不足で何を確認すべきか分からないから。
- コンシェルジュとして、体験候補ごとに推奨理由と不適合理由・注意事項を見たい。**なぜなら**自信を持ってゲストに説明できる根拠が欲しいから。
- コンシェルジュとして、候補の情報源・最終確認日・確信度を見たい。**なぜなら**古い情報や未確認情報をそのままゲストに伝えるリスクを避けたいから。
- コンシェルジュとして、ゲスト向けの提案文(日本語・英語)を自動生成し、自分で編集してから使いたい。**なぜなら**接客中に文章を一から作る時間がないから。
- コンシェルジュとして、AIで十分な候補が出ない場合にワンクリックでデクスターの有人デスクへ相談を引き継ぎたい。**なぜなら**専門性の高い案件は人間の確認が必要だから。
- シニアコンシェルジュとして、過去に自分やチームが対応した類似の相談履歴を検索したい。**なぜなら**同じ調査を繰り返したくないから。
- コンシェルジュとして、体験後のゲストの反応をシステムに記録したい。**なぜなら**次回の提案精度を上げたいから。
- コンシェルジュとして、緊急度(当日/翌日/後日)を設定して相談を送りたい。**なぜなら**デスクモードでの回答の優先順位を伝えたいから。

## ホテル側(管理者・支配人)

- ホテル管理者として、自館の推奨方針・紹介禁止事項を設定したい。**なぜなら**ブランド基準に合わない提案を防ぎたいから。
- ホテル管理者として、スタッフごとのアカウント・権限を管理したい。**なぜなら**在籍状況の変化に応じてアクセスを制御したいから。
- ホテル管理者として、自館の利用状況(相談件数、エスカレーション率等)を確認したい。**なぜなら**契約プランの見直しや投資対効果の説明に使いたいから。
- ホテル管理者として、AIが提示した情報に誤りがあれば報告したい。**なぜなら**次回以降の提案品質に影響するから。

## デクスター側(スタッフ・運用者)

- Dexterデスクスタッフとして、ホテルから受けた相談を、Curator AIの検索結果を使いながら代行入力し、候補を選定したい。**なぜなら**セルフサービスに慣れていないホテルにも同じ品質の提案をしたいから(デスクモード)。
- Dexterデスクスタッフとして、エスカレーションされた相談に、会話履歴・これまでのAI提示候補を引き継いだ状態で対応したい。**なぜなら**ゲストやコンシェルジュに同じ質問を繰り返させたくないから。
- Dexter運用管理者として、体験情報を登録・編集し、公開前に承認したい。**なぜなら**存在しない・古い情報がホテルに提示されるのを防ぎたいから。
- Dexter運用管理者として、情報の最終確認日・有効期限を管理し、更新アラートを受け取りたい。**なぜなら**情報の陳腐化を防ぎたいから。
- Dexter運用管理者として、AIが生成した下書き(月次レポート等)を必ず人間が確認してから配信したい。**なぜなら**AI単独での情報公開を避ける方針だから。
- Dexterシステム管理者として、監査ログとテナント分離の状態を確認したい。**なぜなら**ホテルデータが他ホテルに漏れていないことを保証したいから。

## AI(システム)への要求としてのストーリー
- Curator AIとして、確信度が一定水準を下回る場合、断定的な回答をせず「情報不足」と伝え、有人デスクへのエスカレーションを促したい。**なぜなら**存在しない情報の生成を防ぐ設計原則があるから。
- Curator AIとして、個人情報(氏名・連絡先・パスポート番号等)が入力されようとした場合、警告を表示し入力を抑止したい。**なぜなら**個人情報の不要な蓄積を避けたいから。
