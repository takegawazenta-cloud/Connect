# 回答記録シート・評価表・集計フォーマット・記録方法

## 1. 回答記録シート(1ホテル1シート)

実施時にこの構造でメモを取る(Excel/スプレッドシート化を推奨、ここでは項目定義のみ示す)。

| 項目 | 内容 |
|---|---|
| ホテルID | 例: H-001(実名は別管理、記録シート本体は匿名化) |
| 分類 | ラグジュアリー/シティ/リゾート/旅館/ブティック/チェーン本部 等 |
| 実施日・所要時間 | |
| 回答者役職・人数 | |
| 実施形態 | 対面/オンライン、60分版/30分版 |
| Q1〜Q22 回答(発言ログ) | 各設問ごとに「発言そのまま」列と「記録者の解釈・気づき」列を分けて記載(下記2章参照) |
| 優先仮説への該当メモ | H1〜H8のどれを支持/反証する発言か(下記3章の評価表と連動) |
| フリーコメント | 質問票にない気づき |
| 記録者名 | |

## 2. 発言と事実を分けて記録する方法

インタビュー記録は次の3層構造で残す。**この3層を混在させないことが、後の仮説検証の信頼性を左右する最重要ルール。**

1. **発言(Verbatim)**: 相手が言った言葉をできる限りそのまま記録する。要約・意訳をしない。「」でくくる。
   - 例: 「先月、富裕層のご家族から『地元の人しか知らない場所に行きたい』と言われて、正直どこを勧めればいいか分からなかった」
2. **事実(Fact)**: 発言から読み取れる客観的事実のみを抽出する。感情・評価語を含めない。
   - 例: 「地元密着型の体験提案について、過去に対応に窮した経験がある(発生時期: 先月)」
3. **記録者の解釈・仮説へのタグ付け(Interpretation)**: 記録者がその発言をどう解釈し、どの仮説(H1〜H8)や設計判断に関連付けたかを別欄に書く。ここは主観であることを明記する。
   - 例: 「【解釈】H1(目利き不足仮説)を支持する具体例。地方×富裕層の組み合わせで特に顕著な可能性」

この3層を全設問について分けて記録し、後述の重要度評価表・集計フォーマットは「事実」列のみを集計対象とする(発言・解釈は文脈確認用に参照する)。

## 3. 課題の重要度を比較する評価表

各ホテルへのヒアリング後、聞き取った「困りごと」を以下の軸でスコアリングする(5段階)。

| 課題 | 発生頻度(1〜5) | 対応時間の重さ(1〜5) | 心理的負担(1〜5) | 総合スコア | 該当仮説 |
|---|---|---|---|---|---|
| 地方・専門性の高い体験への対応困難 | | | | | H1 |
| 品質判断ができない(紹介先の信頼性不明) | | | | | H1, H7 |
| 個人の経験・人脈への依存 | | | | | H1, H8 |
| 繁忙時・新人対応での品質低下 | | | | | H1 |
| 予約・変更対応の負荷 | | | | | (業務フロー設計論点) |
| 知見共有の欠如 | | | | | H8 |

- 発生頻度: 1=年数回以下 〜 5=週次以上
- 対応時間の重さ: 1=数分で解決 〜 5=半日以上かかる
- 心理的負担: 1=特に負担感なし 〜 5=強いストレス・自信喪失を伴う
- 総合スコア = 単純平均 or 加重平均(重み付けは全ヒアリング終了後、Phase2で再検討)

## 4. ホテル間で回答を比較できる集計フォーマット

全ホテルの回答を1行1ホテルの横持ち表にまとめる(スプレッドシートのシート2枚目相当)。

| ホテルID | 分類 | 相談頻度 | 平均対応時間 | 最大の困りごと(総合スコア最高) | AIへの期待度(1-5) | AIへの懸念度(1-5) | 支払意思(具体額 or レンジ) | 有料化の根拠成果(自由記述要約) | PoC参加意向(高/中/低) | 決裁者 |
|---|---|---|---|---|---|---|---|---|---|---|

この表により、以下を横断的に確認できるようにする:
- 分類(ラグジュアリー/シティ/旅館等)によって困りごとの傾向・支払意思が異なるか
- 相談頻度と支払意思に相関があるか
- AIへの期待/懸念のパターン(セルフサービスモードへの適性を推定する材料)

## 5. ヒアリング後の仮説更新方法

1. 全ホテル分の回答記録シートを集計フォーマットへ転記する。
2. `00_document_analysis.md` の仮説H1〜H8それぞれについて、支持する発言数・反証する発言数をカウントし、「支持/一部支持/反証/情報不足」の4区分で判定する。
3. 判定結果と根拠発言(3層記録の「発言」列から代表例を1〜2件引用)を1枚のサマリ表にまとめ、Phase2冒頭でデクスターに提示する。
4. 仮説の判定に応じて、Phase2(ペルソナ・利用シーン・差別化・料金仮説)の内容を更新する。特に「支払意思」「サービス形態(デスクモード/セルフサービスモードの比率感)」「PoC参加意向」は料金・MVP設計に直結するため優先的に反映する。
5. 反証された仮説はそのまま削除せず、「反証済み」として記録に残す(将来別の切り口で再検証する可能性があるため)。
