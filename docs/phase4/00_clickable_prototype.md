## 構成(4アートボード)

### 1. Main(コンシェルジュ画面)— 採用中のデザイン案A
Phase3の画面設計のうち、ホテル側が使う主要フローを1つの連続した操作として体験できる:

`ホーム → クイック相談(要望入力) → AIによる追加質問 → 候補一覧 → 候補詳細 → 送付用メッセージ作成(多言語) → 有人デスクへのエスカレーション → 相談履歴`

**デザインの方向性(案A「旅のジャーナル」)**: 「いわゆるビジネスアプリ」の無機質さを避け、親しみと安心感を重視した方向性を採用。
- 暖色系の紙のような背景(アイボリー)、丸みを帯びたカード・ピル型ボタン
- 見出しに明朝体(Shippori Mincho)を使い、編集的・旅の手帖のような雰囲気を演出
- 体験ごとにテーマを表す線画アイコン(マグロ=魚、盆踊り=提灯、忍者=手裏剣)を色付きバッジで表示し、実写真がない状態でも視覚的に親しみやすくしている
- 「田中さん、おはようございます」のように、丸いイニシャルアバターを添えた挨拶で、業務システムというより「担当者に話しかけられている」感覚を意図

**デザインの方向性を比較したい場合**: 別案として案B(おもてなしの温もり: 淡いブラッシュ×深緑、丸ゴシック系のM PLUS Rounded 1cで見出し、より柔らかい)、案C(灯りの案内所: 暖色系の濃紺〜チャコール×琥珀色、行灯のような落ち着いた高級感)のスウォッチをアートボードに並べています(下記4・5)。案Aのままで良いか、B/Cの方向に寄せるか、あるいは要素を組み合わせるか、ご確認のうえお知らせください。

**新機能1: 推薦根拠(レビュー・OTA由来の裏付け)**
候補一覧・体験詳細・送付用メッセージのすべてで、「なぜこの体験が推薦されているか」を示す推薦根拠を表示するようにしました(例: 「Google Maps 4.8★(186件)・Tripadvisor "Travelers' Choice" 掲載・デクスター現地確認済み」)。
**重要な注記**: この評価スコア・レビュー件数は、実際のAPI連携をしていないプロトタイプ段階のため、**すべてデモ用のサンプル値**です。画面上にも「※デモ用サンプル値」と明記し、実データであるかのように誤解されないようにしています。実装時(Phase6以降)は、Dexterが確認した一次情報と、提携先OTA等から取得した実際のレビューデータを組み合わせて表示する想定です。

**新機能2: 送付用メッセージ作成(多言語)**
「体験詳細」から「送付用メッセージを作成する」に進むと、ゲストにそのまま送れる文面(推薦文+体験概要+推薦根拠の要約+料金等の確認事項+予約リンク+結び)を、日本語・English・繁體中文・简体中文・한국어の5言語で生成します。言語を切り替えるとその場で文面が切り替わり、スタッフは自由に編集してから「メッセージをコピー」できます(コピー自体はプロトタイプのためモック動作です)。予約リンクはデモ用のダミーリンクである旨を明記しています。

**Phase0決定2の可視化(変更なし)**: ヘッダーの「コンシェルジュ本人 / Dexterスタッフ代行」切替ボタンで、同じ画面・同じ操作が誰の入力かによって変わることを可視化。

**使用している体験データ**: ホテル提案書(PPTX)記載のサンプル3件。料金・所要時間・予約条件等、原資料に記載のない情報は創作せず「要事業者確認」としている。

### 2. DeskQueue(Dexter運用管理画面)
配色をMainと統一(暖色パレット)。機能は前版から変更なし。

### 3・4. StyleCompare_B / StyleCompare_C(デザイン比較用スウォッチ)
クリック操作はできない静止画的な比較アートボード。ホーム画面相当のミニチュアで、案Bと案Cの雰囲気を確認できる。

## 技術的な位置づけ
この段階はまだ「クリック可能なプロトタイプ」であり、Phase6で作る実際のMVP(認証・マルチテナントDB・RAG・LLM連携等を備えたシステム)とは別物。表示・遷移・ダミーAI応答のみを実装しており、データはすべてブラウザ内の一時的な状態(ページを閉じると消える)。

## 既知の制約・今後の対応
- 実際のAI(RAG検索・生成)、実際のOTA/レビューAPIは接続していない。候補一覧・提案文・推薦根拠の数値はあらかじめ用意した固定のサンプル内容。
- 送付用メッセージは5言語対応としたが、体験の名称(タイトル)自体は日本語のまま据え置いている(実装時は名称の多言語化も検討)。
- 個人情報入力の警告文は表示しているが、実際の入力検知・ブロック機能は未実装(視覚的な注意喚起のみ)。
- モバイル表示の最適化は未検証(Phase3非機能要件ではPC・タブレット優先としており、本プロトタイプもPC幅を前提に設計)。
