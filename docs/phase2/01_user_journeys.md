# 利用シーン・ユーザージャーニー(コンシェルジュ向け)

Phase0決定4により、フロント・インフォメーション担当向けシナリオ(専任コンシェルジュ不在ホテル向け)は対象外とする。全シナリオについて、Phase0決定2の「デスクモード/セルフサービスモード」のどちらに主に該当するかを付記する。

## 詳細記述(代表4シーン)

### シーン1: 富裕層ゲストから抽象的な要望を受ける
- **発生契機**: チェックイン時・滞在中の雑談で「地元の人しか知らない場所に行きたい」等の漠然とした要望
- **利用者の目的**: 要望を具体的な体験候補に翻訳し、ゲストに響く提案をしたい
- **入力情報**: ゲストの国籍・関心領域・滞在日数・予算感・過去の会話メモ
- **システムの処理**: 曖昧な要望から追加質問を提示(会話形式)→条件が固まった時点で候補検索→推奨理由・不適合理由つきで提示
- **出力**: 候補2〜3件、各候補に情報源・確認日・信頼度・要確認事項
- **人による確認**: コンシェルジュが最終的にゲストに合わせて文言調整
- **所要時間目標**: 初回提案まで5分以内(セルフサービス)、または24時間以内(デスクモード、ホテル提案書の既存SLA相当)
- **例外処理**: 十分な情報がない場合はAIが正直に「情報不足」を示し、有人デスクへのエスカレーションを促す
- **成功条件**: ゲストが提案に満足し、体験を実施する
- **蓄積データ**: 要望内容・提示候補・ゲストの反応(採用/不採用)
- **モード**: 主にセルフサービス(即時性重視)。地方・専門性が高い場合はデスクモードへ自動的にエスカレーション。

### シーン2: 地方への2泊3日の滞在案を作る
- **発生契機**: 長期滞在ゲストからテーマ性のある地方旅程の相談
- **利用者の目的**: 移動・宿泊・体験を組み合わせた実行可能な行程を短時間で提示
- **入力情報**: 目的地の希望有無、テーマ(自然・食・工芸等)、移動手段の制約、予算
- **システムの処理**: モデルコース検索・自動生成、地域事業者DBとの突合
- **出力**: 行程案(日程別)、各体験の一次情報区分・確認日
- **人による確認**: 実行可能性(季節・アクセス・予約枠)の最終確認は原則デスクモードで人間が担う
- **所要時間目標**: セルフサービスでの一次案作成は即時、確定版はデスク確認を経て24時間以内
- **例外処理**: 情報が古い・未確認の場合は「要事業者確認」と明示し断定しない
- **成功条件**: 行程がそのまま(または軽微な調整で)ゲストに提示可能な状態
- **蓄積データ**: モデルコースとしてナレッジDBに還流(匿名化した上で)
- **モード**: セルフサービスで初期案作成→デスクモードで実行可能性確認、のハイブリッド。

### シーン3: 当日または翌日の依頼に対応する
- **発生契機**: ゲストからの急な依頼(翌日の予定が空いた等)
- **利用者の目的**: 短時間で信頼できる候補を出す
- **入力情報**: 日程・人数・関心領域
- **システムの処理**: 即時性を優先し、事前確認済み(直近で情報更新済み)の候補のみを優先表示
- **出力**: 候補1〜2件、空き状況は「要確認」フラグ付き
- **人による確認**: 予約可否の最終確認は人間(コンシェルジュまたはデスク)が行う
- **所要時間目標**: セルフサービスなら即時、デスクモードでは通常の24時間SLAを短縮運用する必要がある(要件定義で検討)
- **例外処理**: 候補が見つからない場合、正直に「本日中の対応は難しい」と回答し代替案(翌々日等)を提示
- **成功条件**: ゲストの当日・翌日の予定に間に合う
- **蓄積データ**: 緊急対応の成功率・所要時間
- **モード**: セルフサービス優先(デスクモードのSLAでは間に合わない可能性が高いため)。

### シーン4: デクスターの有人デスクへ相談する(エスカレーション)
- **発生契機**: AI(セルフサービスモード)で十分な候補が出ない、または確信度が低い
- **利用者の目的**: 専門性の高い相談を人間に引き継ぎたい
- **入力情報**: これまでの会話履歴・要望内容が自動的に引き継がれる
- **システムの処理**: エスカレーションチケットを起票し、Dexterスタッフに通知
- **出力**: デスクからの回答(ホテル提案書のSLA=24時間以内に1〜3件)
- **人による確認**: Dexterスタッフによる現地確認・事業者への直接確認
- **所要時間目標**: 24時間以内(ホテル提案書記載の既存実績を踏襲)
- **例外処理**: 24時間で回答できない場合は途中経過を連絡する運用ルールを設ける
- **成功条件**: コンシェルジュがゲストに自信を持って提示できる回答が得られる
- **蓄積データ**: エスカレーション理由・解決までの時間・最終提案内容(AIの弱点把握とナレッジDB強化に活用)
- **モード**: セルフサービスからデスクモードへの接続そのもの。

## その他シーンの要約(詳細はPhase3要件定義で展開)

| シーン | 主なモード | 特記事項 |
|---|---|---|
| OTAにない特別な体験を探す | デスク中心 | Dexterの一次情報の核心価値。掲載率11%(事業計画書記載、未確認・要出典再確認)の体験を扱う想定 |
| 雨天時の代替案を探す | セルフサービス | 即時性重視、天候条件でのフィルタ検索機能が必要 |
| 子ども連れ・三世代旅行への提案 | セルフサービス+一部デスク | 対象ゲスト属性(年齢層・身体的制約)によるフィルタが必要 |
| 食物アレルギー・宗教・身体的制約への配慮 | セルフサービス | 体験データに対応可否フィールドが必須。個人情報(具体的な病名等)は入力させない設計にする |
| 体験後の感想を登録する | セルフサービス | フィードバックがナレッジDBの改善データとして還流(事業計画書のCompounding Loop構想と整合) |
| 過去の類似案件を再利用する | セルフサービス | ホテル内の相談履歴検索。ホテルごとのデータ分離が前提(テナント分離) |

## モード切替の設計原則(Phase3への申し送り)
- 即時性が求められるシーン(当日対応、雨天代替)はセルフサービスを主導線とする
- 一次情報の確度・実行可能性の確認が必要なシーン(地方2泊3日、専門性の高い依頼)はデスクモードへの橋渡しを前提とする
- 「AIの確信度が低い」「情報が古い」場合は自動的にデスクモードへのエスカレーションを促すガードレールを設ける(存在しない情報を断定しないという設計原則の実装箇所)
