# 差別化戦略の仮説

Phase0で整理した差別化仮説を、Phase0決定2(デスク/セルフサービス統合)を踏まえて更新する。

## 差別化の柱(仮説、Phase1検証対象)

1. **一次情報**: デクスターが現地訪問・体験・事業者との直接対話で得た情報。Web/生成AIの二次情報と明確に区別し、UI上で「デクスター確認済み/提携先確認済み/公開情報のみ」を常時表示する。
2. **全国の地域関係者との人的ネットワーク**: DMO・観光協会・専門ガイド・体験事業者との関係(事業計画書の「深い人格的関係」という表現)。
3. **OTAに掲載されていない体験**: 日本の体験事業者の89%がOTA未掲載という構造的空白(事業計画書記載、出典: Skift/トラベルボイス2026年調査と資料内に記載されているが、Claudeは今回この一次ソースを直接確認していない。**未検証の引用として扱う**)。
4. **ホテルが安心して紹介するための品質情報**: 情報源・確認日・信頼度の可視化。存在しない体験・料金・予約枠を生成しないガードレール。
5. **ホテルごとの個別最適化**: ブランド基準・推奨方針・紹介禁止事項をテナントごとに設定できる仕組み。
6. **過去相談と成果の蓄積**: ホテル単位の相談履歴・提案・ゲスト反応の再利用(属人化解消、Phase0 H1・H8仮説)。
7. **【新規、Phase0決定2に基づく差別化仮説】人力とAIの統合運用**: 同一データ基盤・同一品質保証プロセスの上で「Dexterスタッフによる代行(デスク)」と「ホテル自身によるセルフサービス」の両方を提供できる点。競合(汎用生成AI、OTA、DMC)はいずれかの形態しか提供しない。ホテルは自館の習熟度・案件の複雑さに応じてモードを選べる、という柔軟性は他に例がない組み合わせ。
8. **コンシェルジュ業務に特化した入出力**: 汎用生成AIと異なり、ゲスト向け提案文・推奨理由・不適合理由・多言語出力など、接客現場でそのまま使える形式に最適化。
9. **利用ホテルが増えるほど知見が改善する仕組み**(事業計画書のCompounding Loop): 各ホテルの相談・フィードバックがナレッジDBに還流し、Curator AIの精度が向上する。ただしテナント間のデータ越境は起こさない設計が前提(ホテル固有データと共通知見の区分)。
10. **広告料で推薦順位を歪めない方針**: 体験事業者からの掲載料・広告料によって推薦順位を操作しない、という運用方針(要ポリシー明文化、Phase3)。
11. **ホテルブランドを損なう提案を防ぐガバナンス**: ホテルごとの推奨方針・NGリストの反映。

## 模倣されにくい資産の整理

| 資産カテゴリ | 内容 | 模倣難易度の根拠 |
|---|---|---|
| データ | Connectの相談履歴、ホテルごとの相談・フィードバック蓄積 | 時間をかけて蓄積されたプロプライエタリデータ。後発は同量のデータを短期間で得られない |
| ネットワーク | DMO・観光協会・体験事業者・専門ガイドとの人格的関係 | 信頼関係の構築には現地訪問・継続的対話が必要で、資金だけでは即座に複製できない |
| 業務フロー | デスクモード(24時間SLA)+セルフサービスモードの統合運用ノウハウ | オペレーション設計・人員配置・品質管理プロセスは外部から見えにくく、模倣に時間がかかる |
| 顧客関係 | ホテルごとの推奨方針・ブランド基準のカスタマイズ蓄積 | 契約ホテルごとの個別調整の積み重ねはスイッチングコストとして機能する |
| 運用ノウハウ | 存在しない情報を生成しないためのガードレール設計、人間監修プロセス | RAGの実装自体は模倣可能だが、「どの情報を信頼してよいか」の判断基準・監修体制はノウハウの蓄積が必要 |

## 注意(Phase0からの申し送り)
- 上記のうち3(89%未掲載)は事業計画書内の引用であり、Claudeが一次ソースを直接検証したものではない。重要な差別化メッセージとして対外的に使う場合は、事業者側で一次ソース(Skift/トラベルボイス2026年調査)の原典を確認することを推奨する。
- 差別化仮説はいずれもPhase1ヒアリングでの検証対象(競合との比較でホテル側が実際に何を評価するか)であり、現時点では仮説の域を出ない。
